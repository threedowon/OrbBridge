# 메인 서버 하드웨어 진단

## 통합 TXT 로그

메인 서버의 콘솔 출력·오류·게임 이벤트·시리얼 수신·통신 끊김 로그를
`OrbBridge/log/orbbridge_YYYY-MM-DD_HHMMSS_실행ID_001.txt`에 자동으로 저장한다.
각 줄에 PC의 로컬 날짜·시간(밀리초와 시간대 포함)과 로그 종류를 UTF-8로 기록한다.
콘솔 출력도 계속 유지한다. 기존에 제외한 상태 조회와 `/api/admin/hardware/ports`
자동 조회 HTTP 로그는 저장하지 않는다.

파일 하나는 최대 **1,000줄**이며, 1,001번째 줄부터 `_002.txt`처럼 새 파일에 쓴다.
여러 줄 오류도 실제 줄 수로 계산한다. 날짜 변경이나 서버 재시작 시에도 새 파일을 만든다.
기존 로그는 덮어쓰거나 삭제하지 않는다. 실행 파일 배포판은 실행 파일 옆 `log`를 사용한다.

통신 끊김 항목에는 Slave ID, COM 포트, 통신 모드, 마지막 heartbeat 이후 경과 시간과
감지 원인을 기록한다. 정상 heartbeat를 한 번 이상 받은 slave를 감시한다.

- heartbeat가 8초 넘게 없거나 USB/시리얼 입출력 오류가 발생하면 기록한다.
- 같은 끊김은 한 번만 기록하며, heartbeat가 복구된 뒤 다시 끊기면 새 기록을 추가한다.
- 정상 수신도 일반 로그에 저장한다. 사용자의 연결 해제·모드 변경·정상 서버 종료는 통신 끊김으로 기록하지 않는다.
- 웹 화면을 닫아도 서버가 실행 중이면 계속 감시한다. 서버가 종료된 동안은 감시하지 않는다.
- master 경로가 끊기면 그 포트로 통신하던 slave마다 기록한다. 이것이 각 slave 자체의 고장을 의미하지는 않는다.
- 한 번도 heartbeat를 받지 못한 보드는 ID·연결 여부를 확정할 수 없어 기록 대상에서 제외한다.

`start.bat` 또는 `py -m server.launcher`로 실행하고 `http://127.0.0.1:8080/admin`에서 사용한다.
게임과 진단이 하나의 통신 경로를 공유하며 별도 debug 서버는 실행하지 않는다.

## Master ON / OFF

프로그램을 시작하면 항상 **Master ON**이다. 이 설정은 저장되지 않으며 운영
서버의 저장된 통신 설정을 변경하지 않는다. 토글은 실제 master 전원이 아닌 메인 서버의 통신 경로를 바꾼다.

- **ON:** master COM 포트 한 개를 선택한다. 기존 RS485 수신과 LED
  브로드캐스트를 사용한다.
- **OFF:** 테스트할 slave 각각을 PC에 USB로 연결한다. slave 포트들을
  체크박스로 여러 개 선택하고 **연결**을 누른다. 최대 7개 포트를 동시에
  읽으며 LED 테스트는 선택한 slave에만 보낸다. RS485 배선만으로는 사용할 수 없다.
- 경로 변경·연결·해제 시 이전 포트를 닫고 게임을 리셋한 뒤 셀·통계를 초기화한다. 각 경로의 마지막
  포트 선택은 열린 웹 화면에서 유지된다. 선택한 포트가 없으면 미연결 상태로 전환된다.

OFF를 사용하려면 `firmware/slave/slave.ino`를 테스트할 각 보드에 다시 업로드한다.
master 펌웨어는 변경할 필요가 없다. 각 slave의 DIP ID는 서로 달라야 한다.
master에 달린 버튼·홀 센서·디페스타 출력은 ON에서 테스트한다.

slave는 기본적으로 기존 RS485 모드로 부팅한다. USB에서 `U1\n`을 받으면 직접
모드로 전환하며 메인 서버은 1초마다 이를 갱신한다. 직접 모드에서는
RS485 데이터 송신과 RS485 LED 명령 적용을 멈추고 USB로 이벤트를 전달한다.
`C0\n`~`C9\n`은 해당 slave의 LED를 제어하며 RS485로 전달하지 않는다.
정상 해제는 `U0\n`, 프로그램 종료·USB 단절 등으로 갱신이 끊긴 경우에는
5초 후 자동으로 RS485 모드로 돌아간다. 전원 공급과 실행이 유지된 보드에 적용된다.

직접 모드의 USB JSON에는 `transport: "usb"`가 포함된다. 2초마다 heartbeat와
점유 중인 셀의 UID snapshot을 보내므로 연결 전에 올린 오브도 표시된다.
snapshot은 추가 이벤트 통계에 포함하지 않는다. ON에서도 heartbeat 점유 마스크로
현재 셀을 복원하지만, 기존 master 프로토콜에는 전체 UID 조회가 없으므로
added 이벤트를 받기 전까지는 **UID 미확인**으로 표시할 수 있다.

## 생존 상태

오브 제거는 slave에서 **300ms 연속 미검출**을 확인한 뒤 서버에 전달한다.
서버는 이 제거 신호를 즉시 반영한다. 과거의 "배치 후 1초 이내 removed 무시
(접촉 불량 추정)" 보정은 실제 제거까지 늦추므로 제거했다.
제거 신호가 유실되면 heartbeat에서 해당 슬롯이 연속 2회 비어 있을 때 복구한다.
다른 슬롯의 점유 상태가 바뀌어도 해당 슬롯의 복구는 계속 진행한다.

master 자신의 `#master alive relay=… bad=…` 신호로 정상 여부를 판단한다.
slave 데이터가 들어온다는 이유만으로 master 생존 신호를 갱신하지 않는다.
연결 직후에는 하트비트를 기다리고, 8초 넘게 없으면 **응답 없음**, 포트가
닫히면 **연결 끊김**을 표시한다. OFF에서는 master를 **우회 중**으로 표시하며
고장 여부를 판정하지 않는다. 응답 없음은 케이블·펌웨어 문제도 포함할 수 있다.

## 확인 순서

### Master ON에서 LED가 켜진 뒤 꺼지지 않는 경우

슬레이브의 RS485 수신은 13바이트 바이너리 프레임과 `C0`~`C9` LED 명령을
분리해서 처리한다. 이전 문자열 수신 방식은 바이너리 프레임 뒤에 붙은 LED
명령을 버리거나 UID/CRC의 일부를 명령으로 해석할 수 있었다.
수정 적용에는 **각 slave에 `firmware/slave/slave.ino`를 다시 업로드**해야 한다.
같은 폴더의 `LedCommandParser.h`도 필요하다. 서버 재시작만으로는 적용되지 않는다.

업로드 후 Master ON에서 흰색 → 끄기를 반복하고, 오브를 추가·제거하면서도
끄기 상태가 유지되는지 확인한다. 실제 RS485 충돌이나 전원 문제까지 이 수정으로
해결됐다고 보장하지는 않으며, 계속 실패하면 당시 heartbeat와 통신 로그를 확인한다.

수신 파서 회귀 테스트는 Visual Studio 개발자 명령 프롬프트에서 실행할 수 있다:

```bat
cl /nologo /EHsc /W4 tests\led_command_parser_test.cpp /Fo:build\led_command_parser_test.obj /Fe:build\led_command_parser_test.exe
build\led_command_parser_test.exe
```

### 전체 점검

1. 새 slave 펌웨어 업로드 후 ON에서 기존 오브 감지와 LED 테스트를 확인한다.
2. slave 두 개 이상을 각각 USB로 연결하고 OFF에서 해당 포트를 선택한다.
3. 기존에 올라간 오브, 추가·제거, 각 slave의 heartbeat와 LED를 확인한다.
4. USB 하나를 뽑아 해당 포트의 끊김 및 나머지 slave의 정상 수신을 확인한다.
5. ON으로 복귀해 master 수신을 확인한다. OFF 중 메인 서버을 종료하는
   경우에도 보드가 5초 후 RS485 송신을 재개하는지 확인한다.
6. ON에서 master를 분리하거나 응답을 중지해 끊김/응답 없음 표시를 확인한다.

OFF에서 수신한 added/removed는 실제 게임·MIDI·웹 상태에 반영된다. 같은 UID snapshot은 반복 재생하지 않는다.
웹 게임 제어는 `/admin/software`에서 사용한다. OFF일 때 다시듣기·재생·디페스타 버튼이 표시된다.
